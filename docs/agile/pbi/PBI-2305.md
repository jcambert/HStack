# PBI-2305 — Provider Security Parity Tests

**Milestone:** M9. **Status:** Implemented and tested by PR #19 candidate CI #146; main validation pending. **Depends on:** PBI-2302. **Must be addressed before external-provider spikes can become implementation candidates.**

## Existing Solutions Review
M4/M8 security policies, existing Compose/Aspire runtime smoke and Linux CI already validate parts of the native boundary. Extend those same checks through the provider abstraction; do not create weaker sandbox exceptions.

## Work
Build executable tests for provider capability negotiation, host mounts, process UID, read-only filesystem, dropped capabilities, no-new-privileges, no Docker socket/pipe, no host namespace, loopback port binding, corporate CA/TLS, secret scope, durable state and unsafe provider rejection. Run Compose/Aspire baseline and cover failure/rollback.

## Acceptance criteria
- Given a provider without mandatory isolation, when requested, startup is refused with an auditable reason.
- Given native provider under both orchestrators, actual Linux runtime inspection passes all mandatory controls.
- Windows compile/unit checks and cross-platform packaging stay green; document where runtime coverage is not native.
- Existing agents, Herdr, RTK, OpenViking and project isolation regression tests remain green.
- Emit reproducible evidence and trace tested SHA in `docs/agile/M9-REPORT.md`.
