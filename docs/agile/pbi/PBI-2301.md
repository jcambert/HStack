# PBI-2301 — Execution Provider Abstraction

**Milestone:** M9. **Status:** Implemented and tested by PR #19 candidate CI #146; main validation pending. **Blocks:** PBI-2302.

## Existing Solutions Review
Existing `IWorkspaceOrchestrator`, registry, `WorkspaceDeploymentPlan` and Compose/Aspire backends already own orchestration. They must be reused; no duplicate runner. V5 §223 proposes `IExecutionEnvironmentProvider` and §225 capability negotiation.

## Work
Define a stable interface for environment isolation (`Id`, `DetectAsync`, `PlanAsync`, `CreateAsync`, `DestroyAsync`) and typed plans/handles or a minimal compatible equivalent. Separate orchestration lifecycle from isolation *without* double-creating Docker workspaces. Define a capability result and negotiation between orchestrator/provider/agent; forbid any silent security downgrade. Document API and design decisions.

## Acceptance criteria
- Given Compose or Aspire, when planning a native workspace, then effective provider is explicit and capabilities are evaluated before starting.
- Given a mandatory feature is unavailable, when evaluating the combination, then startup is rejected with a diagnostic and no leaked privileged fallback.
- Given existing CLI paths, when migrating the architecture, then invocation and state layout remain compatible.
- Unit tests exercise capability outcomes and serialization/plan boundaries.

**Out of scope:** implementing Dagger, DevPod, VM or remote SSH.
