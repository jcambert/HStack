# M9 research spike — DevPod (PBI-2304)

**Decision for V5:** **NO-GO for immediate HStack provider adoption**, pending a separately authorized and measured prototype with full project/credential/OCI security parity. **Desk research only**; no DevPod workspace was created in this work.

## Upstream sources (checked 2026-10-10)

- https://devpod.sh/docs/managing-providers/add-provider — built-in Docker, Kubernetes, SSH and cloud providers; custom providers.
- https://devpod.sh/docs/managing-providers/what-are-providers — machine versus non-machine execution providers.
- https://devpod.sh/docs/how-it-works/overview — local CLI + injected DevPod agent, SSH/tunnel model, port and credential forwarding.
- https://devpod.sh/docs/developing-providers/agent — agent can forward credentials; requires explicit disablement/proof for HStack.
- https://devpod.sh/docs/getting-started/quickstart-devpod-cli — local Docker quickstart with `devpod provider add docker` and `devpod up ... --ide none`.

## Tradeoffs versus native workspace

| Area | Potential benefit | Integration risk / unknown |
| --- | --- | --- |
| `devcontainer.json` | Portable devcontainer descriptions | HStack does **not** require this file for existing projects |
| Local Docker provider | Reuse native Docker host | Competing project and container lifecycles |
| SSH / IDE | IDE attach workflow | Injected server/tunnel and port exposure need strict scoping |
| Workspace/agent state | Managed remote workspace | HStack's per-project auth/state binds must remain isolated |
| Credential forwarding | Convenience in upstream model | **Forbidden by default** under HStack project-secret policy |
| Runtime security | Configurable devcontainers | Need live read-only/non-root/caps/no-privileged proof |
| Corporate proxy/CA | External environment support | TLS, CA and network behavior must be measured |
| Windows/Linux | DevPod supports multiple hosts | Specific HStack path/mount parity remains unverified |

## Proposed reproducible PoC — not executed

In a throwaway repository and with a reviewed/pinned DevPod binary, configure `devpod provider add docker`, then launch the upstream sample using `devpod up github.com/microsoft/vscode-remote-try-node --ide none`. Before trying a private HStack project: verify whether any credentials/SSH agent/Docker socket are forwarded; ensure those mechanisms are disabled for sandbox workloads; inspect the OCI container for root user, root fs, caps, mount scopes, port binding and host namespaces; compare stop/start/cleanup with HStack; test proxy CA and Windows Docker Desktop, and attempt Herdr/OpenViking/RTK integration only if all mandatory controls pass.

Use controlled disposable credentials only. Do not expose a real project or host HOME, and never treat a successful `devpod up` as security certification.

**PoC execution status:** *not executed*; timings, Windows behavior and credential scope cannot be claimed. No dependency on DevPod introduced into HStack.

**Decision rationale:** current direct Docker provider already serves Compose/Aspire and HStack's project state; introducing DevPod's additional agent, SSH/tunnel, credential and workspace ownership without runtime parity evidence has unjustified risk. No-Go is about **shipping the integration now**, not general viability.
